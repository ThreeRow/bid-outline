# 规则与模型协同提取实现计划

日期：2026-11-09。状态：0.13.0已接入下述主链路与模拟验证；原计划保留，第11节记录实际实现、差异及边界。

## 1. 目标与业务边界

从document-reading产物得到三份可供目录生成使用的A/B/C文本，不回到复杂的要求记录、节点编号或模型归属体系。

- A：格式或集中编制说明中的技术标组成、栏目、编制要求。
- B：技术或服务评审内容，包括具体列项、评价维度和档次中的具体关注点。
- C：其他技术要求中的实质性响应、负偏离限制、必须满足或包含的指标，以及“至少包括、包括但不限于”等明确内容范围。提交方案、证明、承诺仅是其中一种表达，不能继续作为C的唯一边界。
- C指标和约束先保存为依据，不逐条强制成为目录标题。★、☆、▲、△、■本身均可作为候选位置内的定位标识，不要求事先确定含义才使用；模型结合上下文判断其是否技术相关、实际约束什么。符号含义仍按本文件及所在位置理解，不预设跨文件语义。
- 定位必须先有位置范围：规则识别候选章节，加上模型根据目录提出的章节，再在这些范围内匹配各类词、表达和符号。不以全文任意命中直接认定类别或回取大范围。
- 旧category-routing-1仍为待定方案。新计划不沿用“A/B关键词命中必然压掉C”的优先级；同一位置可以有多种实际用途，不因减少调用而删掉内容。
- 所有新prompt先做可替换占位，最终任务表述和输入输出样例由用户参与定稿。

## 2. 最终编排

```text
document-reading产物（优先复用本轮24份已有产物）
  → 程序建立章节/表格/原文位置索引
  → 章节/标题规则找候选位置 ＋ 模型看目录辅助判断A/B/C位置
  → 合并候选章节和相关附表位置，保留多用途类别线索
  → 只在候选位置内匹配关键词、表达、★☆▲△■等标识
  → 宽泛/不明确线索：截取局部上下文 → 模型判断是否需要
       不需要：排除此命中位置
       需要：回取对应完整小节/条目及共同条件
       不确定/调用失败：记录待核，不按“不需要”删除
  → 明确位置或通过局部判断的位置，形成完整候选正文
  → 结构分块，大块继续细分，小块在共同语境下合并
  → 分块文本train批量调用：
       直接判断并整理内容
       或多点锚定 → 固定Python模板回取原文
  → 按类别和原文顺序拼接块结果
  → 按A/B/C分别统一整理内容与格式
  → A.txt / B.txt / C.txt
  → 原有N02-A/N02-B、AB融合、C补充、最终润色
```

“规则+目录辅助”不是互相替代。目录辅助可以找到规则未覆盖的章节叫法；最终搜索范围是两者提出的位置的并集，并按原文显式引用补充可取得的章节。C候选位置可以分布在多个大章，但不是无范围的全文关键词扫描。目录缺失、位置无法确定时，先根据正文中的标题或给模型补充结构概览确定候选区域，不能静默退回全文盲匹配。

“局部判断”与后面的“完整块整理”是两种输入规模：前者用于低特异性命中的取舍，后者在需要的位置上处理完整内容。明确的技术组成/评审条目可直接进入完整候选，不必每个命中额外增加一次判断。

直接整理和锚定提取共用候选范围入口，不要求每个块重复执行两条路径。默认先打通直接整理；锚定方式在同一批候选上作可比较的替代路径，避免直接混成不可归因的多轮流程。

## 3. 规则与范围：先离线改进

当前`document/locate.py`将位置词同时用于章节和正文，并以相邻DocumentElement扩展。一个Element可能是整张大表，导致S21/S23整表混入。C正则又偏向提交动作，未覆盖用户修正后的范围。

计划拆分职责：

| 文件 | 计划职责 |
|---|---|
| `document/location_rules.py`（新增） | 分开的候选章节模式与区域内线索，含C约束/指标/列举/提交表达及符号；记录是否需局部判断 |
| `document/source_index.py`（新增） | 章节范围、段落、表行/单元格、原文顺序及规范化字符到原文的映射 |
| `document/locate.py`（改造） | 先确定候选位置，再在范围内匹配；局部判断通过后回取完整范围，不把字符串命中当确定类别 |
| `document/organization.py`（替换或收缩） | 只根据已选范围及类别线索规划整理任务，不用固定A/B优先级排除C |

位置规则参考`docs/内容对应关键词分析/24份招标样本技术目录依据汇总.md`第二节及三个分组报告：

| 类别 | 候选位置 | 范围内寻找的内容 |
|---|---|---|
| A | 投标/响应文件格式、编制与组成说明、模板、相关须知/前附表及附件 | 技术组成、方案/材料栏目、编制说明和明确层级 |
| B | 评标/评审办法、评分标准/细则、定性评审及附表 | 技术或服务评审项目、具体内容、评价维度和档次细节 |
| C | 技术条款、项目/采购需求、技术需求书、技术规范书、投标人等须知/前附表；根据结构线索补充相关商务条款、合同和附件 | 实质性响应、偏离限制、必需指标、内容列举、符号标记及相关材料要求 |

这些是候选位置，不是互斥类别；不能因章名含商务或合同就整体排除，也不能把整章当作已确认的技术要求。

规则改进分为：

1. 标题入口用模式覆盖须知、磋商/谈判须知、文件组成/编制/格式、评标/评分/定性评审等叫法；附件只作查找入口，再找技术组成或方案条目，不能整章照收。
2. 正文中的章节引用、评分词和实际标题分开处理。例如需求中“系统识别评审标准”不能仅凭该词认定为本项目评分表。
3. C在候选位置内分组检索实质性响应、偏离效力、必需指标、内容列举和材料提交。★、☆、▲、△、■作为可直接命中的定位标识；取标记对应条目及附近定义/表头，模型判断实际用途，不能因含义尚未解析就不选。单独“不得负偏离”的说明和实际受约束条款需保持关联。
4. 匹配保留段落/行边界；空格归一化不能将无关段落拼成一句。需要定位偏移时有可逆位置映射。
5. 范围按完整小节、条目或评分行组扩展，止于对应结构边界；不再默认拿前一整张表。跨表续句按连续条目处理，表头和合并父标签作上下文。
6. 明确区分负责原文和辅助上下文，候选范围重叠合并，来源顺序稳定。一个单格含多条内容时支持格内文字范围，不只选整行。
7. “至少包括、包括但不限于”等宽泛表达先取有界局部上下文（小标题、引导句、相邻完整段落或表行及父标签），由模型判断是否为所需内容。不需要则排除此命中位置；需要才回取完整条目并进入后续分块。不因一句宽词就发整章或整表。重叠局部上下文先合并，同一处多个宽词不重复调用。

先修改规则/边界、再测24份，不同时修改prompt来掩盖规则效果。旧基线报告保持原样。

## 4. 目录辅助与局部模型处理

建议增加独立任务，名称暂定，编号不复用旧P语义：

| 任务 | 输入 | 输出及后继 |
|---|---|---|
| E01 目录辅助定位 | 完整章节目录、必要表格标题及任务说明 | 复制原文标题，给可能的A/B/C位置；程序映射原有章节 |
| E00 局部相关性判断 | 候选位置内宽泛表达或不明确标识的有界上下文 | 简单判断保留/排除/待核；保留才回取完整内容，不在此抄录全部要求 |
| N01-A/B/C（重写占位） | 对应候选范围的完整块及共同上下文 | 同一次调用完成判断与相关内容整理，不再额外先判断一次 |
| E02 多点定位 | 一份候选完整块 | 原文起始句、结束句、中间代表性锚点及位置线索 |
| E03-A/B/C 汇总整理 | 同类块结果按来源顺序拼接 | 统一内容和格式的A/B/C文本，供目录生成 |

目录模型不生成任意路径或要求程序依一个新标题猜位置。模型输出标题未找到、重复匹配时，程序提供候选标题及局部上下文作有限澄清；无唯一结果则保留不确定位置，不默默取第一项。

E00仅用于筛除局部弱线索，不替代所有块的整理；输出约定保持为短结论及必要的一句说明。程序区分判断结论与通信/空答/解析失败，失败不算排除。输入带命中位置、所属章节、标记或表达及必要共同条件，不要求模型输出原文偏移或复杂业务记录。被排除的命中保留证据，不因一处排除而抹去同区域其他已确认命中。

分块任务保留来源类别的预期，不默认每块跑ABC。多用途或不明确位置可以带对应多个类别线索，按有限目标分别整理。此策略由新的候选结构与样例验证确定，不提前固化category-routing-1的排除逻辑。

大块按内部小节、条目及表格语义关系切分；小块在同章、同任务和相同共同条件下合并。按材料处理量与完整请求预算双重约束，不能只看能否塞进窗口。

## 5. 多点锚定与固定Python提取模板

新增`document/anchors.py`，负责执行固定的定位/截取操作。模型填写参数，不必自由生成整段Python。

模型文本保持简单，示意：

```text
类别：C
位置：技术要求 / 其他要求
起始句：原文中实际存在的一句
中间锚点：原文中有代表性的短句（可多条）
结束句：原文中实际存在的一句
```

程序处理：

- 限定在本次给出的原文范围内查找；标题、句子和锚点均检查实际存在。
- 起止句确定边界，中间锚点按原文顺序位于范围内，用于排除重复出现位置。
- 返回所有匹配候选及明确的唯一/多处/未找到结果；不默认第一处、最短范围或最长范围正确。
- 唯一匹配后回取原文，保存章节、element、表格行/cell及展开文本范围，明确定位精度。
- 多处或未找到时，只提供局部候选让模型补充/修正一次；仍未解决则记录范围问题，可显式回退直接块整理，不隐式扩大到全文。
- 起止跨不同表或段落时，按索引原文顺序取范围；一段中有多次相似短语时用字符位置区分。

只对这些最少定位参数做确定性解析；业务内容继续用普通文本，不引入每条要求的复杂字段和ID。保存原始模型回复，参数解析失败不能当“没有相关内容”。

## 6. 汇总整理与输出衔接

现状：`text_runner.py`将每个N01结果直接分别交N02生成，缺少用户提出的类别级统一整理。

新增拼接和E03任务：

1. 每块结果携带程序维护的来源信息，以原文顺序加入对应类别。
2. 拼接保留简短来源章节标题；程序不根据相似标题自行删除不同原文。
3. E03处理重复边界、跨块续句、共同条件及格式，不生成目录，不删除B的明确评价维度，不将C只缩成方案提交清单。
4. 某类全部材料能容纳时，一次完成该类汇总；超预算时先做保持来源分组的局部汇总，再整体汇总。仍不能容纳时保留分册文本与未完成标记，不截断、遗漏批次或无限摘要。
5. 存储`organized/A.md、B.md、C.md`及块来源依赖；目录生成入口改为使用这些采用文本。

没有候选、模型明确未发现、模型失败、空答案和处理不完整分别记录；不强迫自由文本回答都填一组固定状态字段。不使用简单搜索“无相关”来猜模型整篇结论。

## 7. 优先文本train与真正批量

当前`src/bid_outline/model/train_client.py`虽然发送query_list，但列表只有一个任务；现有执行器按任务保存一张ticket。`document-reading/runtime/train_api.py`具备批量相关实现，可参考协议及用例，但不能未经核对直接替换其重试/采用行为。

计划新增train批量调度，配合`model/executor.py`及现有客户端：

- 同阶段就绪的独立块任务组成有界query_list，串行依赖的汇总/目录任务等待前驱。
- 每条任务仍独立做指纹、缓存、完整预算及调用额度核对；单请求窗口按每条query计算，批量条数/总负载另设配置。
- 批次保存唯一responseId、成员query_id及共享原始审计；任务通过引用关联批次，结果按query_id关联，不按返回顺序。
- 批次终态后逐任务判断可用性和采用；一个空答案或失败不覆盖其他成功任务。部分进度结果不提前冒充终态。
- 恢复沿已保存的同一ticket轮询，已采用任务不重交；提交结果不明时不整批重提。重新请求明确失败任务时只提交这些任务，并记录前后关系。
- 并发以逻辑query负载与批次数分别约束，不能把一个大批次当一个普通请求绕过现有并发上限；取消及审计失败保持原边界。

服务支持的批次大小通过后续小批实测确定，不先硬编码未核实值。新实验优先train，不再默认用OpenAI做阅读调用。若本轮只复用已有reading产物，则不重跑阅读。

## 9. 实施顺序及验收

| 顺序 | 交付 | 验证 |
|---|---|---|
| 1 | 更新C业务定义、位置入口与区域内规则及范围索引 | 24份已有阅读产物离线回放；检查匹配是否限定候选位置，补充符号和C新范围样例 |
| 2 | train批量执行与逐条恢复 | 模拟乱序、部分终态、缺失ID、单条失败、空答案、取消、审计失败和重启，确认不重复提交 |
| 3 | 目录辅助E01与局部判断E00 | 先确定位置；宽泛词通过短上下文判断后才扩为完整候选；排除、待核和失败分别验证 |
| 4 | 分块判断整理、拼接和E03汇总；只到ABC阶段入口 | 固定文本验证按源序衔接、共有条件、缺类/失败及长输入，不冒充模型能力 |
| 5 | 多点锚定E02及Python模板 | 同一候选集对比直接整理与定位回取；测同名锚点、跨表、多锚点顺序和错引 |
| 6 | 用户参与prompt定稿，小批train验证，再扩到24份 | 分开报告规则定位、原文回取、ABC整理和下游目录质量 |

前4步形成“位置→区域内匹配→局部取舍→完整块整理→类别汇总”的可运行链路，再加入多点定位回取的对照路径。正式实测时先抽取能代表已知问题的少量文件，明确输入量、输出和失败情况后再扩大；不把306项旧离线回归当新流程已测。

24份测试沿用样本编号，但原79条正向短语探针不能覆盖用户新定义的C。需要从既有分析报告和原文中追加负偏离/实质性条款、本地符号定义、必需指标、包括但不限于及例外等代表性证据，同时保留履约、纯业务规则、普通参数等边界反例；不声称建立了全文金标准。增加相同符号在技术/商务/节能清单中不同用途、宽泛词相关/无关局部上下文、排除命中不影响同区其他命中、模型判断失败不导致静默丢弃等用例。

优先检查：真实正文是否取全、候选是否带入无关大表、约束与适用条件是否保留、B列项与维度是否丢失、批量任务是否独立可恢复。调用数和token减少只作负载指标，不能单独证明质量改善。

## 12. Prompt复核及阈值感知适配计划（待实施）

本节对应用户随后审阅的13份自然语言草稿及长输入要求。只规划，不直接替换prompt正文或业务代码。0.13.0占位模板与会话草稿是两个版本，不能把草稿当成已经上线。

### 12.1 Prompt复核结论

| 问题 | 草稿或当前实现中的例子 | 适配原则 |
|---|---|---|
| 引入任务之外的替代行为 | “不生成目录”“不输出提取代码”“不分别建立优良中差目录”等 | 用正面产物说明替代，只保留实际决定返回形式的最少约定；不罗列模型没有被要求做的事 |
| 缩写先行仍在程序包装中 | E00的“类别：C”、N01的“整理类别：C” | 单类任务直接给自然语言目标；多类定位先讲三类内容，再定义A/B/C |
| train仍套用聊天消息话术 | train_query增加独立任务前言、“系统说明”“用户消息”编号 | 文本任务发送一份连贯说明，任务与资料用`---`分隔；旧P任务保留兼容序列化 |
| 整理阶段过早归并 | N01-B中的“同一意思合并表达” | 块处理优先沿原句完整整理；跨块去重、接续和格式统一交给实际需要的整合调用 |
| 示例中的项目主题可能被照搬 | N02-B固定使用范本适配、工具提供等特定项目内容 | 以通用列项规则解释；如需示例，用明确示意或当前输入中的真实片段，测试原文没有示例主题时不得凭空出现 |
| 业务对象边界可能失真 | 技术/商务标签、人员证件、现场演示与方案混合 | 正面说明选取实际用于技术评审或技术响应的内容；保留原文对象形式，不能只凭章名判断 |
| A产物类型已改变，后继仍按旧类型处理 | 新草稿N01-A直接返回目录，当前E03-A仍汇总要求、之后又N02-A | 将A视为目录草稿；A整合负责合并草稿，默认调用链退出N02-A |
| N03输入类型不清 | “当前完整草稿”可能已经含A/B，草稿模板却固定说两份分别为A/B | 程序明确标记格式目录、评审目录、累计融合草稿的真实角色，不给累计草稿贴错误标签 |
| “去掉重复”过强 | 相同标题可能属于不同包别、不同章或条件 | 仅同来源边界重复及实际相同内容可合并，保留不同条件；最后润色不承担新一轮业务概括 |
| 空结果口径未衔接 | E02原代码识别“未发现”，草稿统一“无”；普通任务的“无”仍传给下游 | 对适用任务统一精确整答“无”，解析后标记无内容，保留审计但不进入汇总/目录；空字符串、异常和不完整结果不等于“无” |
| 来源提示可能进入目录 | A输出目录，汇总输入仍有“来源区域”行 | 来源用于输入理解和程序依赖；最终A目录及N05只呈现实际标题，不把来源标签变成标题 |

每份prompt使用“角色→材料来源/解析形态→实际章节及必要上下文→本次目标→返回内容→分隔线→原文”组织。局部判断、标题定位、原文锚点保留必要控制格式，业务整理和目录不增加JSON或节点字段。根据经验用于识别材料用途，实际内容仍以输入为依据。

章节、表头、共同条件只由一次统一渲染生成，不把同一信息分别写进模板和材料再重复。起止锚点等说明中的字段格式属于任务必需，不能把它们与范围外否定项一起删除。

### 12.2 已有能力与复用位置

| 当前代码 | 已有能力 | 本次动作 |
|---|---|---|
| `model/budget.py::TokenBudget.text_tokens` | 本地fast tokenizer与计数缓存 | 直接复用作材料量计数，不新增估算器 |
| `TokenBudget.allowance/check/count` | 完整提示、train实际拼接、生成额度及安全余量 | 保留为唯一硬预算准入；更新渲染后规划与实际请求使用相同序列化 |
| `document/token_chunks.py::token_chunks` | 按章/小节/列表/表行分层规划、完整请求fits | 作为长输入和硬预算超限时的原文切分器，不重写语义切分系统 |
| `document/chunks.py::split_chunk` | 负责范围再拆、来源和共同条件 | 复用截断/超限恢复；无安全拆分明确保留失败 |
| `document/text_chunks.py::expandable_tables` | 大单格的限定精度展开切片 | 传入本次实际切分目标；不在短输入还可单次执行时提前按3000拆表 |
| `workflow/text_runner.py::organize` | 材料包装、原文分块、bounded_map并发、源序输出 | 增加规划判定，正常输入绕过主动小块切分，长输入复用现有分块路径 |
| `text_runner.py::generation_batches`、`model/packing.py::pack_items` | 文本分批、完整记录打包 | 复用处理整理结果或目录批次；不将拆原文与拆结果混为一套字符截断 |
| `workflow/extraction.py::summarize` | 对应E03任务、有限层次、失败保留分册 | 改为按需调用，优先判断合并后的完整输入是否可单次处理，不再固定3000导致每层过碎 |
| `model/train_batch.py`及executor | 逻辑任务并发、query_list微批、逐条采用/共享恢复 | 原样复用；阈值是每条query的材料量，与批次条数分开 |

目前差异：`organize`总按text_batch_tokens=3000约束分块；`CollaborativeRunner.run`随后无条件调用summarize，即使只有一个短块。新策略是调整这些现有决策点，不新建第二套执行器或独立长文处理流水线。

### 12.3 阈值语义与编排

建议配置：`long_input_threshold_tokens=9000`、`split_target_tokens=4000`，均可调整。计数对象是本次待处理材料及其必要章节/共同上下文，不把任务prompt长度当模型阅读的正文量；完整请求能否发送仍统一交TokenBudget判断。

首先恢复“逻辑材料单元”：同类别、同候选位置的完整章节/小节/条目，保持源序和条件。当前locate将同类别多处选区放在一个Document中，不能直接用这个类别总量决定把无关章节合成一次请求。复用token_chunks的章节分组规则，保留每个逻辑单元的计划身份。

```text
逻辑材料单元
  → 完整渲染 + 既有token计数/硬预算检查
  → 材料token ≤ 阈值 且 请求fits：一次处理
  → 材料token > 阈值 或 请求不fits：
      复用token_chunks/split_chunk
      以4000为目标、按真实剩余额度缩小，优先完整语义单元
      → 有界并行独立整理
      → 按源序拼接全部有效结果
      → 对应E03单次整合（若完整输入在阈值和窗口内）
```

4000是触发拆分后的目标，不能继续作为所有请求的硬材料上限。允许未超过9000的中等输入一次执行。阈值附近以实际计数判断，等于阈值允许单次；实际prompt很长而窗口不足时仍拆分。

切分层需要按实际执行任务渲染预算：direct使用N01；anchors使用E02。当前organize在anchors路径仍以N01提示做规划，应同步修正；一次锚点修正或回退N01也重新计量。

若整合输入仍超过感知阈值或硬窗口，就复用summarize的有限分组/层级整合。先检查全组可行性，再决定分组；每层保留所有完整输出及父依赖。整合也不能因“只是汇总”而绕过感知限制。不能安全处理、失败组或不收敛时保留完整分册及incomplete，不截断或声称完成一次完整整合。

短单元处理后不重复整合自身。类别存在多处独立位置时，仍按用户要求在源序拼接后作必要的类别级合并；如果长单元结果已整合且它就是该类别唯一输入，复用此结果，不再调用一次相同E03。实现时由来源分组和是否已合并的计划状态决定，不能只看输出长度猜测是否已整理。

E00小上下文判断继续用自身局部边界；E01目录分页继续复用现有完整预算。原文整理和E03整合共用阈值判定函数，但使用不同的结构切分方式与任务模板；下游目录任务本轮继续既有完整请求预算，不额外扩展成所有阶段都必须多一次调用的固定流程。

### 12.4 Prompt和程序的具体适配位置

1. `model/prompts/text/`：按用户草稿修订E01/E00/N01/E02/E03/N02-B/N03/N04/N05，移除范围外说明；A直接生成目录并由E03-A按需合并。
2. `model/text_tasks.py::render`：构造单一完整文本，任务说明与输入正文以`---`分开；不重复附通用system指令、章节占位和材料标签。
3. `model/train_client.py::train_query`：新文本任务支持将该单一query原样发送，不再额外包“系统说明/用户消息”；保留旧P调用兼容。OpenAI备选可同样发送一条完整user文本。`TokenBudget.count`、真实wire_request和微批组装统一使用同一个序列化入口。
4. `config.py`与配置样例：加入两个可调参数；text_batch_tokens停止控制新整理路径，旧流程保留兼容说明，避免简单改名使旧语义混入。
5. `workflow/text_runner.py::organize/generation_batches`：添加同一套轻量判定，实际切分/并发继续用已有函数；导出触发原因、材料量、实际任务和分块计划。
6. `workflow/extraction.py::summarize/anchors`：按需整合、统一精确“无”、锚点首次及修正后都识别同一约定；原文回取成功后A需要走一次生成目录，不能将原文误当目录。
7. `workflow/collaborative_runner.py::run`：根据实际产物区分A目录与B/C要求文本；A直接参与融合，N02-A退出默认调用链但暂留历史注册。删除固定“每类总要汇总”的冗余调用。
8. `model/executor.py`或新文本结果规范化函数：只对适用任务精确识别整答“无”；保留原始回复及程序内empty标记，包含“无”字的正常正文不误判。E00三态不按这个规则替换。空答继续报错。
9. 文本任务版本、流程/代码版本、配置及渲染指纹同步更新；旧run不可作为新prompt恢复。公共文档与CODE_GUIDE描述最终调用链。

阈值只决定执行路径，不应写入自然语言prompt要求模型自行判断token数量。新任务不会因为增加计划元信息而让模型输出程序ID。

### 12.5 实施顺序和检查

1. 先完成prompt审阅稿与产物约定：确认A输出目录、B/C输出原句要求、无内容精确“无”；更新统一渲染和序列化测试。
2. 同步调用链、空结果和A锚点路径，确保不重复生成A、不把“无”及来源标签传成目录依据。
3. 在既有计数/切块/汇总上接入阈值决策，记录计划，不改变train批量和审计原理。
4. 离线验证实际rendered query：角色/背景在前，单类任务无未定义字母，输入有分隔线，不含范围外负面说明，无示例项目污染。
5. 测阈值下/等于/超过、阈值下硬预算不足、长表/跨表、辅助条件占用、锚点任务实际提示预算；同长度短单次和长多次的调用数可明确断言。
6. 测并行乱序仍按原文拼接；分块失败保留范围；汇总输入过长有限整合；多处同类只合并一次；单短块不固定E03；A锚定后转目录；空结果全类跳过；仅部分空不丢其他输出。
7. 测新序列化预算和train单条/批量实际query完全一致，恢复不会复用旧渲染；执行完整离线回归。
8. 用已有24份reading产物离线输出新阈值计划，比较调用数、块大小和计划路径；这不能验证模型整理不丢失。后续再按用户确认的prompt做少量文本train长输入对照，先验证内容保真再扩到24份。

本节规划尚未修改prompt正文、渲染、业务调用或阈值配置。本轮没有执行测试或真实服务请求；代码现状仍以第11节及当前实现为准。
