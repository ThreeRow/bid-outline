# 当前模型服务调用说明

核对日期：2026-11-10；对应应用版本0.15.2。本文依据当前客户端实现及用户确认的train参数语义；没有新增服务探测或模型调用。服务内部实现未随仓库提供。

## 1. 服务入口

服务根地址：`http://10.21.150.137:50007`。当前项目优先使用支持批量的文本train接口。

| 用途 | 方法与路径 | 输入形式 |
|---|---|---|
| 提交train作业 | `POST /api/v2/chat_train` | `query_list`，每条是一份完整文本query |
| 查询train结果 | `POST /api/v2/get_resp_data` | `response_id` |
| OpenAI兼容聊天 | `POST /v1/chat/completions` | `messages`，区分system/user |

train配置base_url使用根地址，不带`/api/v2`。客户端兼容去掉末尾`/v1`。配置中的model仅作为train审计标签，未传给train服务；实际模型由服务路由决定。OpenAI接口则需传真实服务模型名。

如服务需要认证，设置环境变量`BID_OUTLINE_API_KEY`，客户端添加`Authorization: Bearer ...`。密钥不写入配置、文档或示例请求。历史无认证成功不表示服务始终无需认证。

## 2. 重要区别：max_tokens的含义

用户已明确确认：**train接口的max_tokens是模型总窗口限制，20K/40K指这个参数，不是最大输出tokens。**

| 项目字段／接口参数 | 含义 | 当前映射 |
|---|---|---|
| 配置`service_context_tokens` | 服务的总模型窗口 | train实际`query_list[].max_tokens` |
| 配置`context_tokens` | 本地采用的逻辑窗口 | 本地预算取它与service_context_tokens的较小值 |
| 配置`max_tokens` | 本地为生成预留的额度 | train不将它作为输出限制发送；OpenAI则用作最大输出tokens |
| train实际`max_tokens` | 总模型窗口 | 默认配置20480；配置服务窗口40000时发送40000 |
| OpenAI实际`max_tokens` | 最大输出额度 | 默认配置8192 |

本地仍检查：输入tokens＋生成预留tokens＋安全余量≤min(context_tokens, service_context_tokens)。tokenizer与服务端模板兼容性尚未核实，不能称计数为服务精确值。

例如保守本地预算可以设context_tokens=20480、service_context_tokens=40000、max_tokens=8192：本地继续按20480准入，train发送的窗口则是40000。40000/40960必须按实际部署确定，不能把“40K”自行解释为固定的其中一个数值。默认示例未擅自改窗，仍为20480。

**8192在train模式下只是本地生成预留，不能保证服务恰好最多输出8192。** 本接口适配未提供单独的train输出上限参数。

## 3. 提交请求

以下为请求结构示例，任务内容需替换为实际材料：

```json
{
  "query_list": [
    {
      "id": "sample-01-task-01",
      "query": "你是招投标领域的专家。\n\n请整理以下技术要求，优先沿用原句。\n\n---\n\n截取内容所属章节：采购需求\n\n本次资料：\n实际截取原文",
      "timeout": 3600,
      "temperature": 0.0,
      "max_tokens": 20480,
      "res_type": "str",
      "level": 0,
      "enable_thinking": 0
    }
  ]
}
```

| 字段 | 当前客户端约定 |
|---|---|
| `id` | 每条逻辑任务的唯一身份，返回结果按此关联，不按列表顺序关联 |
| `query` | 一份独立完整文本；角色、背景、任务及返回要求在前，`---`之后是章节、正文和必要补充 |
| `timeout` | 发送给服务的作业超时参数，单位秒；具体内部计时规则需服务端确认 |
| `temperature` | 当前准确性测试用0，不构成无遗漏保证 |
| `max_tokens` | 总模型窗口，来自service_context_tokens |
| `res_type` | 当前固定为`str` |
| `level` | 当前固定默认0；客户端允许0—2，业务语义未在此臆测 |
| `enable_thinking` | 整数0或1；当前测试关闭，即0 |

多个独立query可以放在同一query_list中，每条携带自己的id与完整文本。当前项目有真实两条微批记录，但未验证任意批次大小或吞吐上限。

提交成功后示意返回：

```json
{"status": 1, "responseId": "service-job-id", "msg": "...", "data": []}
```

取得responseId后立即保存票据，再开始轮询。提交网络中断但是否接收不明时，不盲目重新提交；先检查持久化请求、回执与票据。

## 4. 查询结果

请求：

```json
{"response_id": "service-job-id"}
```

进行中示意：

```json
{"status": 1, "msg": "任务进行中", "data": []}
```

终态示意：

```json
{
  "status": 1,
  "msg": "任务完成",
  "data": [
    {"id": "sample-01-task-01", "is_success": true, "answer": "整理后的文本", "message": "成功"}
  ]
}
```

顶层status=1、HTTP 200或“任务完成”都不能单独表示每条模型任务成功。逐项检查id、is_success和answer。当前实现等待整个批次终态后逐项采用；进行中的partial data不先当最终答案。一个成员失败不抹去其他成功成员。

终态失败的实际表现之一：

```json
{"id": "sample-01-task-01", "is_success": false, "answer": "", "message": "请求超时，请稍后重试!"}
```

这是服务返回的任务级失败，与HTTP超时、客户端轮询期限耗尽不同。缺少服务内部日志时不能进一步断言是排队还是推理超时。空正文同样不能当作“无相关要求”。服务缺少finish_reason时，客户端目前会默认stop，因而也不能仅据stop推断内容完整。

## 5. 并发与三层超时

| 配置 | 默认值 | 本次24份测试采用值 | 含义 |
|---|---:|---:|---|
| `timeout_seconds` | 120 | 600 | 单次HTTP操作超时 |
| `train_timeout_seconds` | 600 | 3600 | 请求中的timeout，交给服务的任务期限参数 |
| `train_poll_timeout_seconds` | 1200 | 7200 | 客户端整体轮询期限 |
| `train_poll_interval_seconds` | 2 | 5 | 两次轮询之间的等待秒数 |

只延长HTTP超时不能解决服务主动返回的任务超时。轮询期限应留足任务执行及排队余量；服务是否接受更长期限，以实际响应为准。

单文件max_in_flight限制逻辑请求在途数；train_batch_size控制每批query数，实际不超过max_in_flight；train_max_batches限制该文件同时在途批次数。批处理脚本还控制parallel_files，总逻辑上限为parallel_files×max_in_flight。当前默认批量入口为5文件×4请求＝20条；每文件2条query一批、最多2批在途。服务端真正并行执行多少不由这些客户端设置保证。

## 6. 项目运行方式

配置示例：`configs/train.text.example.json`。现有阅读产物可直接运行：

```bash
PYTHONPATH=src python -m bid_outline doctor --config configs/train.text.example.json
PYTHONPATH=src python -m bid_outline run --reader reading \
  --input /path/to/reading --config configs/train.text.example.json \
  --run /path/to/new-run --stop-after directory
```

doctor默认只验证本地配置，显示train_wire_max_tokens和local_generation_reserve_tokens；train没有在本仓库约定非生成健康接口。

24份已有reading批量入口：

```bash
python scripts/run_reading_batch.py --output runs/new-reading-generation-batch \
  --parallel-files 5 --concurrency 4 --max-total-in-flight 20 \
  --train-batch-size 2 --http-timeout 600 --task-timeout 3600 --poll-timeout 7200
```

这条命令会实际调用模型，输出目录必须新建。它冻结src及prompt，保留每个文件独立run、日志和票据。查看batch.json/progress.md；终态与是否产出目录、语义质量分开判断。

## 7. 载荷核对、恢复和历史错误

- `calls/.../request.json`是统一逻辑请求，其中max_tokens仍表示本地生成预留，不能直接当train wire参数。
- `calls/.../request.http.json`保存实际单条载荷或微批成员载荷。
- `train_batches/batch-*/train.submit.request.json`保存实际批量HTTP请求；其中max_tokens才是本次传给train的总窗口。
- `train.ticket.json`和共享ticket.json保存responseId；响应、终态、原始输出均保留。

恢复用原run、原配置及对应代码版本，优先轮询原票据，不盲目重新提交。已有冻结快照不会被当前源码修改自动更新。

0.15.2前客户端误将8192生成预留传成train总窗口，`runs/reading24_directory_c20_v0151_01`使用的是旧冻结版本。用户已告知该任务结束；此次未改写其输入、输出或审计。旧实验出现的失败、遗漏不能全部归因于模型能力，后续要在正确窗口下复核。本次修正本地回归415项通过，尚未新增真实模型复测。
