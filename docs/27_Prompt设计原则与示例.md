# Prompt设计原则与示例

更新：2026-11-10。适用当前E/N文本流程；模板版本`separated-material-provider-2`。本文记录本对话已确认的设计原则及示例，不自动替换运行模板，不代表真实模型质量验收。

## 1. 一次请求如何组织

每次调用都是独立任务，不能假定模型知道前面的对话、ABC定义或上次调用。

按以下顺序组织：

1. 角色：简短说明领域，例如“你是招投标领域的专家”。
2. 背景和输入：说明材料来自招标文件、实际是什么内容；必要时提醒Word和表格转换可能导致排版混乱。
3. 当前任务：明确本次识别、整理、定位、生成或融合什么。
4. 返回要求：只规定本次所需产物及必要格式、无内容约定。
5. `---`分隔线。
6. 本次资料：实际章节信息、完整负责正文、必要补充；有修正反馈时也在资料区单独标明。

任务说明先讲完，所有来源资料放在分隔线后。不能在背景和任务之间插入大段原文、表格或辅助材料。原文中的路径、花括号、编号和分隔符原样保留，模板不能再次解释或替换原文中的占位字样。

## 2. 任务范围和措辞

- 一次调用承担一个清楚的主要任务，减少复杂判断、规则体系和程序字段负担。
- 正面说明“做什么、返回什么”，不添加“不生成目录、不输出代码、不写正文”等本次未要求的替代行为。
- 输出形式是必要约定。例如“只返回目录、以缩进表示层级”应保留。
- 角色、任务、章节和目标不重复提供。模板已经说明单类目标，程序无需再拼一遍“本次寻找内容”。
- 单类任务使用完整业务名称；需要ABC简称时，先解释三类内容，再定义简称。
- 实际章节由程序填入，不把示例中的章节名称写死在模板里。
- 示例只帮助理解表达形式，不将固定项目名、产品模块或技术主题灌入通用prompt。
- “根据经验”用于判断材料用途；内容依据仍来自本次材料，不能编造能力、人员、指标或履约承诺。
- 以实际调用模型的能力为准。不要让模型同时承担稳定ID、来源偏移、父子引用、复杂JSON和业务理解。

## 3. ABC职责和产物

| 类别 | 业务含义 | 整理阶段的产物 |
|---|---|---|
| A | 技术部分格式、组成、指定栏目、模板和编制要求 | 直接形成目录草稿，保留原名、顺序及明确层级 |
| B | 技术或服务评审、评分项目、列项及评价维度 | 优先沿原句整理评审要求，随后单独展开目录 |
| C | 技术需求、实质性响应、负偏离限制、必需指标、明确内容范围和相关响应事项 | 优先沿原句整理要求，供目录补充参考 |

C不能收窄为“投标时提交哪些方案或证明”。“至少包括、包括但不限于”后的具体内容、条件和指标也可能属于C。★☆▲△■可定位，但没有跨文件统一效力；根据本处说明理解。

B展开目录时，原文明确的完整性、思路清晰度、先进性、合规性、可扩展性、可操作性等维度要显式呈现。不要用更抽象的理解把它们省掉。优良中差的差异整理为关注要求，不生成四套目录，也不将优档细节全当否决条件。

C的数值和约束先作为编制依据，不要求每个数值都成为标题。后续编排为A目录与B目录融合，再按C补充，最后单独润色。

## 4. 保真与分块的边界

关键词负责定位完整章节或小节，不负责决定该块哪些行能保留。定位到相关块后，程序应完整回取，不要求每个子项再次命中关键词。

这是输入构造的责任，不能靠prompt补救。例如“总体技术方案”包含（1）—（4），如果（1）（2）在程序选区中被删掉，模型无法恢复它们。

块内整理优先忠实保留原句、列项、数量、范围、共同条件、例外、否定和义务强度；不以压缩为目标。重复边界处理、分块接续和格式统一交整合阶段。不同包别、适用条件或响应对象不能因标题相近就合并。

长输入由程序检查感知阈值和完整请求预算。当前初值为9000材料tokens，触发后以4000正文tokens为切分目标；并行独立处理，按源序拼接，再按需整合。阈值和token计数不交给模型自行判断，不在prompt中加入分块调度或并发要求。

补充上下文只保留确需的表头、引导条件等。负责正文中已有的精确重复不再附加；整段展开表格不能因为末尾冒号就当作共同引导句。显式来源条件也不能为了短而随意截断。数据放置正确与补充范围正确是两项检查。

## 5. train与OpenAI的组织方式

两种接口共用业务模板和资料，不共用错误的角色文字包装。

| 接口 | 实际发送形式 | 审计展示 |
|---|---|---|
| train | 一份完整query：角色＋任务说明＋分隔线＋资料 | `input.md`等于query，不加裸`user`前缀 |
| OpenAI兼容 | system保存角色，user保存任务说明、分隔线和资料 | JSON保留角色；`input.md`用明确角色标题展示 |

train内部逻辑请求用单条user消息承载，不等于query正文要写“user”。旧P多角色请求有历史兼容序列化，不应误套到新E/N任务。

实际query、预算计算、单条/批量wire及input.md应一致。OpenAI消息结构也需按实际provider计量。接口参数不写进业务prompt，详见[26号模型服务调用说明](26_模型服务调用说明.md)。尤其train的`max_tokens`是总窗口，OpenAI同名字段是最大输出，不能混为一谈。

## 6. 返回约定

- 业务整理：普通文本或列表，优先沿原句；不加额外过程解释。
- 目录：只用缩进表示层级，不加Markdown标记、章节编号或解释；最终最多四级。
- 定位：只用必要的真实章节路径，或原文起始句、结束句、中间锚点。原文锚点回取使用固定程序，不执行任意模型代码。
- E00局部判断：首行“保留／排除／待核”，必要时简短理由；信息不足不强判排除。
- 其他适用任务没有相关内容时整答“无”。程序只精确识别去除首尾空白后恰好为“无”，不将“无负偏离要求”“说明：无”“无。”自动当空结果。
- 空字符串、超时、截断、解析失败不等于没有相关要求。已有非空目录后继返回“无”，不能抹掉原稿或冒充完成。

## 7. 示例

以下均为设计示例，资料用短片段展示；运行时应提供真实完整块。示例中的原文只供说明，不写入通用模板。

### 示例一：train整理技术评审要求

```text
你是招投标领域的专家。

以下是从招标文件中截取的评审内容，可能混合技术、商务和价格要求。文字由Word及表格转换而来，格式可能混乱。

请识别技术部分的评审或评分要求，并按原有项目整理。保留项目下面的具体列项、评价维度和各档评价的具体内容。

只返回整理出的技术评审要求，优先沿用原句。没有相关内容时，直接回复“无”。

---

截取内容所属章节：
第二章 评标办法 / 技术评审

本次资料：
评审项目：总体技术方案
方案应包括：（1）系统建设；（2）接口对接；（3）运维服务。
根据完整性、思路清晰度、先进性和可操作性进行评审。
```

这里不添加“不生成目录”。完整列项由程序送入，不能只发送命中“技术”“服务”的部分行。

### 示例二：A识别编制要求并直接出目录

```text
你是招投标领域的专家。

以下是招标文件中的格式与编制说明，可能包含表格转换后的内容。
请识别技术部分的组成和目录要求，并根据原文生成目录大纲，保留指定栏目名称、顺序和明确层级。

只返回目录，用缩进表示层级，不加Markdown标记、章节编号或额外解释。没有相关内容时，直接回复“无”。

---

截取内容所属章节：
第五章 投标文件格式 / 技术部分

本次资料：
技术部分包括：总体技术方案、项目实施方案、售后服务方案。
项目实施方案下设人员安排和实施计划。
```

A已经产出目录，后继直接采用或按需合并，不再固定调用一次同样的目录生成任务。

### 示例三：C整理技术要求及响应事项

```text
你是招投标领域的专家。

以下是从招标文件中截取的技术需求，文字由Word及表格转换而来，格式可能混乱。
请识别技术部分需要响应的要求，并整理出来，保留实质性响应、负偏离限制、必需指标和明确内容范围，以及数量、条件、例外和约束后果。

只返回相关要求，优先沿用原句。没有相关内容时，直接回复“无”。

---

截取内容所属章节：
第四章 采购需求

本次资料：
★系统响应时间不超过2秒，不允许负偏离。
实施方案至少包括部署、联调、试运行和验收安排。

补充上下文：
本节指标适用于所有部署节点。
```

“本节指标适用于所有部署节点”是来源条件，不得插到角色与任务之间，也不能当成程序对模型的系统指令。

### 示例四：多类目录定位与局部判断

多类任务先解释业务，再定义简称：

```text
你是招投标领域的专家。

我们需要从招标文件中寻找三类依据：技术部分的格式和编制要求，以下简称A类；技术或服务评审要求，以下简称B类；技术需求和需要响应的约束、指标及内容范围，以下简称C类。

下面提供真实章节目录。请指出可能包含这些内容的位置，只选已有完整章节路径。同一位置可以对应多类。
每行返回“A：章节路径”“B：章节路径”或“C：章节路径”；没有可能位置时回复“无”。

---

本次资料：
第一章 投标人须知
第二章 评标办法
第四章 采购需求
第五章 投标文件格式
```

单类E00则只介绍本次寻找目标和局部材料，要求“保留／排除／待核”，不用重新讲整套ABC。局部判断确认位置后，程序回取完整结构块。

### 示例五：B展开目录

任务说明可写为：

```text
请以评审项目作为一级标题，将项目明确列出的内容和评审维度逐项展开为下级标题。保留输入中实际出现的维度，具体细节放入对应内容下面。
只返回缩进目录，不加Markdown标记、章节编号或额外解释。
```

对示例一的材料，可以得到：

```text
总体技术方案
    系统建设
    接口对接
    运维服务
    完整性
    思路清晰度
    先进性
    可操作性
```

这是一段说明预期行为的文档示例，不把这些项目主题固定加入N02-B通用模板。

### 示例六：同一任务的OpenAI消息

```json
[
  {"role":"system","content":"你是招投标领域的专家。"},
  {"role":"user","content":"以下是从招标文件中截取的技术需求。请识别需要响应的要求，优先沿原句整理。只返回相关要求，没有则回复“无”。\n\n---\n\n截取内容所属章节：第四章 采购需求\n\n本次资料：\n系统响应时间不超过2秒。"}
]
```

同一业务在train中把角色与user内容直接连成一份query，不增加“系统说明”“用户消息1”或裸角色标签。

## 8. 修改和检查方法

先审查业务任务是否单一、独立成立，再查看真实渲染输入，而不只读模板txt：

1. 章节正文及列项是否从前序完整取回；与原阅读产物核对，不只核对已选块内部。
2. 所有来源资料是否在分隔线后；说明是否被辅助原文打断。
3. 是否重复目标、使用未定义简称、添加范围外禁止项或固定项目示例。
4. train的query、预算、input.md与单条/批量wire是否一致；OpenAI是否保留角色结构。
5. 无内容、空答、异常、截断是否分别处理；A/B/C产物与下一阶段是否一致。
6. 切分后负责正文是否完整覆盖原候选，源序是否保持；共同条件是否确有必要。
7. 真实输出是否保留关键条目；机械通过不代表语义正确。接口窗口参数错误时，先纠正接口，不把所有遗漏归因模型能力。

模板、输入、参数或代码变更后使用新run，历史审计和失败证据保留。最终prompt设计需用户参与，示例不是自动发布的新模板。
